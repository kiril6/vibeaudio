# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VibeAudio: a zero-dependency Node.js CLI (`vibe <command>`) that wraps any AI coding tool (Claude Code, Gemini, Codex, etc.), playing procedurally-generated focus music while the wrapped command runs and an outcome chime when it exits. All audio is synthesized in pure JS (no MP3 assets, no native bindings) and played natively across macOS (AVAudioPlayer/`afplay`), Linux (`paplay`/`ffplay`/`aplay`), and Windows (PowerShell `SoundPlayer`).

## Commands

```bash
npm test                              # runs test/test-synth.js (plain node + assert, no framework)
node bin/vibeaudio.js <command>       # run the CLI locally without installing
node bin/vibeaudio.js --preview jazz  # audition one genre loop
node bin/vibeaudio.js --clear-cache   # force audio regeneration after a synth change
npm link                              # to test the `vibe`/`vibeaudio` global bin locally
```

There is no build step, linter, or bundler — it's plain CommonJS Node (`engines.node >= 18`). To run a single check, just run `node test/test-synth.js` (the whole file is one linear script of assertions; there's no per-test filtering).

**Audio cache keys are derived from `synthFingerprint()`** (hashing `src/synth/*.js`), so editing any generator automatically invalidates and regenerates cache entries. Run `--clear-cache` to purge stale renders.

## Architecture

**Entry points**: `bin/vibeaudio.js` → `src/cli.js#run()`. `run()` branches:
- `--mcp` flag → `src/mcp.js#startMcpServer()` (stdio JSON-RPC server for desktop apps)
- a `HOOK_ACTIONS` flag → `runHookAction()` → `src/hooks.js` (Claude Code hooks)
- `--preview` / `--clear-cache` / `--status` / `--stop` → one-shot utility paths
- no command args + interactive TTY → `src/interactive.js#promptInteractive()` (menu to pick AI tool / delivery / genre / volume / reactive)
- command args given → `executeCommand()` spawns the wrapped command directly

**The wrapper flow** (`src/cli.js#executeCommand`): spawns the child command with `stdio: "inherit"`. A grace timer (default 1500ms, see `--grace`/`VIBE_GRACE_MS`) delays starting audio — if the child exits before the grace window, no music/chime plays at all.

The wrapper measures **child process lifetime**, which equals working time only for commands that exit when their work is done. An interactive REPL stays alive while the user reads and types, so `hooksAlreadyCover()` suppresses the wrapper's music entirely when the child is `claude` (without `-p`/`--print`) and our hooks are installed — otherwise `vibe claude` layers a session-long stream over the hook daemon's per-prompt one. With no hooks installed, that same case prints a one-line pointer to `--install-hooks` rather than silently doing the wrong thing. This matters because the interactive menu (`vibe` with no args) launches Claude Code through exactly this path.

Exit handling is the subtle part, and two invariants must hold:
- **`cleanup()` runs exactly once**, guarded by a `finished` flag. Both the signal path and the `close` path route through it; without the guard the HUD prints twice and the player is stopped twice (the second stop re-enabling the chime the first one suppressed).
- **A signal-killed child reports `code === null`.** `close` must map that through `signalExitCode(signal)` to `128 + signum`, never to `0` — otherwise an aborted run claims success, plays the success chime, and lets `vibe claude && deploy` chain after a `Ctrl+C`. Interrupts also suppress the chime entirely.

**Audio pipeline** (`src/player.js`):
- `AudioPlayer.start(genre, volume, { maxDurationMs })` schedules `playLoop()` on a timer derived from the WAV's own header (`wavDurationMs`), re-spawning `LOOP_OVERLAP_MS` (120ms) early so the loops' boundary fades crossfade instead of leaving a process-spawn gap. It returns `false` if already playing with identical settings, and restarts when genre/volume differ — so an MCP genre switch isn't silently dropped.
- Tier selection ("adaptive time escalation") happens per loop iteration: tier 1 (0-15s), tier 2 (15-45s), tier 3 (45s+). **Every generator must honour its `tier` argument** — one that ignores it writes three byte-identical cache files and silently disables escalation.
- A piece is `LOOP_BARS` (3) bars, cycled per loop iteration and reset to bar 0 by `start()`. Tiers stop changing at 45s, so before this every turn past its first minute was one file on repeat — ~85 identical plays across ten minutes, ~250 across half an hour, which is where someone reaches for `--mute` and does not come back. The bar is passed down to the generators, **not** mixed into the seed: each genre carries exactly three curated variants, so three salted seeds would land on three different ones only 2 times in 9, while rotating the index is distinct by construction (`rotate()` in `generator.js`, test [51]). Bar 0 is the unrotated variant and renders byte-identically to the pre-bars loop, so upgrading does not change what a project opens on — which is also why test [43]'s pins still hold. Cache cost is 3x the loops per project.
- `resolveGenre()` maps aliases (`chiptune`→`8bit`, `bossa`→`jazz`, …) to canonical names and resolves `random` **once** at `start()`, not per loop — otherwise the genre would change every ~6s. `random` draws from `SHUFFLE_GENRES`, not `AVAILABLE_GENRES`: `drone` is excluded because it is the deliberate "no melody at all" choice, and rolling it by chance reads as broken audio rather than as variety. A new genre belongs in both lists unless it is similarly non-musical.
- Cache files are written to a `.tmp` beside the target and **renamed into place**, never written at the final path. `existsSync` goes true the instant a file is created, so a plain write of a ~1 MB loop left a window in which a second process (another agent's daemon, a wrapper run, MCP) saw the path, spawned the backend at it and played a torn WAV. Reproduced 4 runs in 5; test [36]d races four processes at one uncached loop and checks each one's bytes against its own header.
- Generated WAVs are cached at `~/.vibeaudio/cache/v<pkg.version>-<synth hash>/s<seed>/`. The key is what makes synth changes reach existing users, and it is **derived, not declared**: `synthFingerprint()` hashes the contents of every `src/synth/*.js`, so changing a generator invalidates the cache whether or not anyone remembers to bump the version. It used to key on the version alone, and that failed 40 commits running — eight of the ten generators changed while the version sat at 0.2.0, so the mechanism documented as delivering audio fixes had never once fired. The version stays in the directory name for legibility only. Costs 0.3 ms at startup. Stale key directories are pruned when a new one is created, and seed directories are pruned to the 3 most recent projects — but never one touched within `PRUNE_MIN_AGE_MS` (10s), which may be another process's render in flight. Deleting it between that process's `mkdirSync` and its write threw ENOENT on the playback path; `writeCacheFileAtomic()` recreates the directory and retries once for the window the floor leaves open.
- `projectSeed()` hashes `process.cwd()` (overridable via `--seed`/`VIBE_SEED`), so a repo always sounds like itself. This is deliberately **not** per-run: focus music should fade into the background, and per-session novelty works against that. The seed is resolved once in `start()` and held on the player, so tiers within a run stay the same piece.
- Playback backend is detected once from `PLAYER_CANDIDATES` (`afplay` → `paplay` → `ffplay` → `aplay`, plus PowerShell `SoundPlayer` on Windows). If nothing is found, it warns once and runs silently — audio must never block the wrapped command.
- `aplay` and PowerShell `SoundPlayer` take no volume argument. `bakedGain()` decides per backend: 1 when the player attenuates itself (macOS and most Linux keep the existing cache files, bit-identical), otherwise the volume, which `applyGain()` scales into the PCM and `gainSuffix()` puts in the cache filename (`loop_jazz_t2_g25.wav`). **Exactly one of the two must apply** — a file that is both pre-scaled and passed to `-v` is attenuated twice.
- **macOS fades through a helper, not afplay** (`src/mac-player.jxa`, #12/#18): one `osascript -l JavaScript` process drives `AVAudioPlayer`, and `playLoop()` writes `play <volume> <fade-in> <path>` to its stdin instead of spawning an afplay per loop. The first loop fades in over `FADE_IN_S`; later ones carry their own baked boundary fades. **Closing its stdin is the stop**: it fades out over 0.3s and exits, so a daemon killed with SIGKILL cannot orphan music (verified live) and `killProcs()` ends the pipe rather than signalling. JXA hands `NSData.length` back as a *string*, so `data.length === 0` never fires and the helper hangs at end of input - it is `Number()`ed. Startup is ~80ms. A helper that cannot start, or dies, is dropped for the rest of the process and the loop replayed with afplay; `VIBE_NO_FADE=1` forces afplay (the suite sets it, because its fake `afplay` on PATH would otherwise be walked past). Chimes still use afplay. **Live volume**: a daemon spawned by hooks with no volume typed on their command line carries `--follow-volume` and re-reads the saved volume every poll (`volumeSource` = `volumeNow`), so `vibe --volume` reaches music already playing - `AudioPlayer.setVolume()` sends the helper `volume <v> <ramp>`, and other backends take it at the next loop. A volume *pinned* by an old install or typed is not followed: a flag outranks the file. Not done, and still open on #12: in-process crossfades, and the Linux (#16) and Windows (#17) backends.
- A module-level `process.on("exit")` hook kills live player processes, so an abrupt exit can't orphan audio.
- **Settings have one home: `~/.vibeaudio/config.json`** (`loadConfig()`/`saveConfig()`). Genre and volume used to live in three unrelated places — an env var only the wrapper read, a value baked into seven hook command lines at install time, and an MCP client's `env` block — so "set my genre" had three answers and the hooks' answer was "reinstall". The README needed a table to explain which one applied. `hookCommand()` therefore writes **no** `--genre`/`--volume`: each hook fires as a fresh process, parses its own argv, and reads the file, so a change lands on the next prompt with nothing reinstalled. Precedence is flag > env > file > default, resolved in `parseArgs()` and mirrored in `mcp.js` — an export still wins in the shell that set it, and `vibe --genre 8bit npm test` stays a one-off. `--reactive` **is** still baked, because it is not a setting the music reads: it decides which hook entries exist, and a resume respawning the daemon has to carry it. `installHookTargets()` (cli.js, not `installHooks()`) does the saving, keeping the installer a pure config edit tests can point at a throwaway file. An install from before this pins its own settings and, being a flag, still wins — `--status` and `saveDefaults()` both say so rather than letting a saved default do nothing audible.
- `--here` saves under `projects["<cwd>"]` in the same file and is resolved by **walking up** from the cwd (`projectSettings()`), so an agent launched from a subdirectory still finds what was saved at the repo root. `projectSeed()` keys on the exact directory instead, which is tolerable for an arrangement nobody chose and would not be for a genre somebody did — don't make them match by making this one exact. The map is not pruned: each entry is a deliberate choice worth a few bytes.
- The menu's genre question takes `p` to audition the highlighted entry (`playPreview()`/`stopPreview()` in interactive.js). One module-level child process, killed by the next press and by `cleanup()` on every exit from the menu — there is one pair of speakers, so a second press must silence the first. Gated on `playbackDisabled()`, unlike `--preview`: a mute is set for a call, and the keypress is not worth surprising someone mid-call. A loop renders in ~150ms, which is why this can be synchronous.
- `daemonPlaying()` reads the running daemon's genre and volume out of its own **command line** (`ps`), not a state file it would have to keep in step - `spawnDaemon()` already puts them there, and a process that dies without cleanup cannot leave a stale answer. It answers the question a running daemon raises and `--status`'s Sound section cannot: a genre saved a moment ago does not reach music already in the air until the next prompt. Both `--status` and `saveDefaults()` say so rather than letting the setting look inert. posix-only, like `isOurDaemon()`, which shares the lookup.
- **No install scripts.** A `postinstall` used to print the starting commands on a global install. npm now gates install scripts behind `allow-scripts` (observed on 11.17), so there the script never ran: every install ended with a warning instead, and that warning made the package look broken (seen live in the warning's own suggestion, `npm install -g --allow-scripts=vibeaudio`, which names no package and so installs the current directory). Removed in favour of what needs no script: the README and site pair the install with its next step (`npm i -g vibeaudio && vibe --install-hooks`), and `vibe` with no arguments opens the guided menu. Do not add one back; "no install scripts" is also a trust signal for a global CLI.
- **Update notice** (`src/update.js`): the one network request VibeAudio makes. `updateNotice()` is synchronous and offline — it prints what the last check saved to `~/.vibeaudio/update.json` and, if that is a day old, spawns a detached copy of `update.js` to fetch `registry.npmjs.org/vibeaudio/latest` for next time, so no run ever waits on the network. Printed only by `--help`, `--status` and the menu, and only to a TTY: hook output goes to the agent, and a wrapped command owns its terminal. Silent under `CI`, `NO_UPDATE_NOTIFIER`, `VIBE_NO_UPDATE_CHECK` and npx (where `npm i -g` is the wrong advice). It sends nothing about the user, and the README says so — keep both true.
- A reinstall **inherits what the old entries pinned** for any setting the user did not type and has not saved (`pinnedSettingsFor()` in cli.js). Migrating off the pinned scheme is not the moment someone's music should change: those entries are the record of what they have been hearing, and the config file may not exist yet. Two guards, both found by doing it live and watching the wrong thing happen — an install reported `lofi @ 40%` over a user's synthwave, and then a second version nearly let four untouched installs outvote a genre chosen a minute earlier. So: pins are adopted **only when every target being installed agrees** (the config is one value for the machine; "first one found" is not an answer), and **only for a key with nothing saved** — a pin fills a gap, it never overrides. `--reactive` is deliberately *not* inherited: dropping the flag is the documented way to turn it off, and there would be no other.
- A settings flag with **no command after it** saves the default (`saveDefaults()`), rather than falling through to the launcher menu, which then asked for a genre and used its own answer: `vibe --genre jazz` — the most natural phrasing — used to do something else entirely, and the README had to warn about it. `parseArgs()` returns `typed`, what was on *this* command line, which is the only way to tell that apart from a genre merely in effect.
- Muting has two front doors and one gate. `VIBE_DISABLE` suits a shell you want permanently quiet; `--mute`/`--unmute` (`setMuted()`) writes `~/.vibeaudio/muted` for the case the env var cannot reach — a hook is a child of the agent and inherits the environment the agent had at launch, so a variable exported later never arrives, and restarting the agent is precisely what you cannot do while a call is ringing. A file crosses that boundary. `--mute` also calls `stopDaemon()`, because silencing the *next* prompt is no use when the current one is already playing, and `playLoop()` re-checks so a wrapper run (which has no daemon to stop) goes quiet at its next loop boundary. The mute **expires** (`DEFAULT_MUTE_MINUTES`, 60; `--mute 0` opts into indefinite): an unbounded mute the user forgets is indistinguishable from the tool being broken, and nothing would ever surface it — `--status` is a net only for someone who already suspects. `muteState()` clears an expired file as it reads it, so the state converges from whichever process notices first rather than needing a cleanup pass.
- **`--doctor`'s output check** (`src/output.js`, macOS only) reads the default output device (`system_profiler SPAudioDataType -json`) and the volume settings (`osascript`), because `afplay` plays on the *default* output device, which moves when a monitor connects - and a display often has no system volume (`output volume:missing value`, which is not zero) and quiet speakers. It reports only facts: muted, no volume control, system volume under 10%. A guess such as "this genre at this volume is too quiet" was left out on purpose - speculative checks nag, and a doctor that cries wolf gets ignored. A failed lookup yields no finding, not a failure.
- **Turn history and `--report`** (`src/history.js`): `hookStart` stamps `started` and `blockedMs` on the session file, `hookWait`/`hookResume` accumulate the time spent blocked on the user (`waitStart`), and `hookStop` appends one JSON line to `~/.vibeaudio/history.jsonl` - project (payload `cwd`), `ms`, `blockedMs`, outcome. Only a session with a recorded `started` is logged: a guessed duration would poison every total. `recordTurn()` never throws (a log is not worth failing a hook) and trims itself to the last 4000 lines past 1 MB; `VIBE_NO_HISTORY` skips it. Wrapper runs are **not** logged: a child's lifetime is not an agent's working time (see the wrapper-flow note). `--report` reports "You waited" as `ms - blockedMs` and the blocked time on its own line, because slow-agent and absent-user are different complaints. Each line also carries `session` and `chimed`, for **"Back to it"** (`returnTimes()`): the gap from one turn's end to the next turn's start (`at - ms`) in the same session — sessions, not projects, because two agents in one repo interleave; lines from before `session` was logged pair by project. Gaps over `RETURN_WINDOW_MS` (30 min) are breaks and dropped, or a lunch would swamp the median. The gap is split by the *finished* turn's `chimed` once both sides have five, which is the evidence for what the chime is worth. `chimed` is `!noChime && !playbackDisabled()` at stop time — it assumes a backend exists, since a machine with none plays no music either. Verified by test [57].
- **Key-matched success chime**: `GENRE_KEYS` (player.js) records the key each generator sits in, read off the generators, and `chimeKeyFor()` picks it; `generateSuccessChime(duration, key)` plays that key's tonic chord. The default key's output is byte-identical to the original chime, and its cache file keeps the old name. `random` is deliberately *not* resolved a second time for the chime, and noise genres keep the default. Only the success chime is keyed: failure and attention are fixed by what they mean.
- **Notifications** (`--notify`/`--no-notify`, `notify` in config.json, `VIBE_NOTIFY`): the answer to "which session?", which a chime cannot give. `hookStop` and `hookWait` already know the session; `notify()` in hooks.js adds one detached `osascript`/`notify-send` spawn naming the project (payload `cwd`, else the hook's own). Title and body travel as **argv**, never spliced into script text - a project directory is user-controlled. Off by default, read by each hook process from the config file like every other setting (nothing baked into hook commands), gated by `playbackDisabled()` so a mute silences banners too, and never allowed to fail the hook: a missing notifier is swallowed. No Windows backend yet (`notifyCommand` returns null).
- **Music off** (`--music on|off`, `music` in config.json, `VIBE_MUSIC`, `--here`) is the signals without the music, and it is **not** a mute: `playbackDisabled()` silences everything including the chimes, `musicEnabled()` (player.js) silences only the loop. A setting of its own rather than a `none` genre, so `genre` survives it and `random`, `GENRE_KEYS` and the menu preview never meet a non-genre. Precedence is the usual flag > env > `--here` > file > default; parseArgs() resolves it (`music`, `typed.music`) and hands the boolean to the three places that start music, so a one-off `vibe --music on npm test` beats a saved off. Those are `hookStart()` and `hookResume()` (skip `spawnDaemon()`; the session file, events, `notify()` and the chime path are untouched, and `hookStart` still calls `stopDaemon()` first so a switch lands on the next prompt) and `executeCommand()` (no `player.start()`, no HUD; `musicStarted` still goes true after the grace window so the exit chime plays). `vibe_play` checks it directly and says so, like a mute. Deliberately **not** gated inside `AudioPlayer.start()`: that gate cannot see a flag, and `--preview` is an explicit request to hear something. The stuck heartbeat is a layer on the music, so with music off `hookResume()` plays `generateStuckChime()` once on the crossing instead (the same lub-dub from `tension.js`, standalone, detached, skipped with `--no-chime` or a mute; with music on the daemon's layer covers it, so no second sound). Test [68]. Not built: the menu's "signals only" delivery choice. Saving off does not stop music already playing (`saveDefaults()` says so), same as a genre change. Test [67] runs it through the real hook commands, with music on as the control for "no daemon". Verified live: wrapper with a fake `afplay` plays the loop and the chime with music on, only the chime with it off.
- **`--announce`** (`announce()` in hooks.js, #35, test [73]) is the signals for something that is not an agent turn: a chime for the outcome (`--outcome`, or `--exit-code` where 0 is success; both together is an error), the `--notify` banner (`banner()`, which `notify()` now wraps) and an `announced` event with `source: "cli"`, `text`, `outcome` and a null session. It never starts the daemon, touches a session or stops music. The chime is played **detached**, so the script that called it does not wait out the chime. The text is argv only, control characters become spaces, capped at `ANNOUNCE_MAX_CHARS` (200); an empty text is an error. A repeat of the same text within `ANNOUNCE_REPEAT_MS` (5 s, kept in `~/.vibeaudio/announce.json`) is dropped *whole*, event included, because it is the loop that has to be quiet. A mute silences the sound and the banner but still writes the event, as for every event. Exit 0 whatever the playback does (`cmd; vibe --announce ...` must not turn a pipeline red); only misuse, which is the caller's own mistake, exits 1. The three flags are in `VALUE_FLAGS`, so a trailing `vibe --announce` is an error and not a wrapped command. Verified by test [73] with a stub backend; not run against real speakers, because the developer's machine was muted.
- **`--dashboard`** (`src/dashboard.js`, #36, test [74]) is a read-only page of what `--events` already says: `followEvents()` feeds Server-Sent Events, and after each event the server pushes a fresh `agentState()`, because an event says what changed and the page wants the list. One follower per open page (a 250 ms stat each), capped at 20 pages. It is **local by construction**: bound to `127.0.0.1`; every request's `Host` must be `127.0.0.1:<port>` or `localhost:<port>` or it is a 403 (DNS rebinding: a hostile page can point its own name at loopback, and the browser then sends that name); no CORS headers; only `GET`/`HEAD`; and a CSP that names the page's one script by its SHA-256, computed from the script actually served (the test checks the match), so no other script can run in it. The page builds its DOM with `textContent` only, since project paths and tool names are not ours. **Read-only in v1 on purpose:** a mute or stop button would need CSRF protection from every other tab first. Port: 4747 by default, falling back to a free one; an explicit `--port` that is taken is an error. Foreground, Ctrl+C. The "how long in this state" is first-seen time on the page; `agentState()` gained `waitingSince` (the wait's start) so a waiting row does not show the turn's age. Not done: playing the signals in the browser (binding beyond localhost changes the security model), and running as a service. Verified in a real browser (Playwright, macOS) against seeded sessions; `docs/dashboard.png` is that capture. The screenshot server was started on a throwaway `HOME`.
- **`--statusline`** is `formatStatusline(agentState())` and nothing else: `agentState()` is the only reader of session files, so there is no second notion of state to keep in step. Idle prints nothing, not even a newline; otherwise the most urgent status, `×N` when more than one session is in *that* state (not in any state), and `: <project>` for a waiting session. No colour (tmux and Starship style it themselves), no `ps`, no tier (the tier lives in the daemon and is not public state), not gated by a mute. Test [66]. Both README snippets were run for real (tmux 3.x with an attached client in the Terminal panel, reading its rendered screen; Starship 1.26.0 via `starship prompt`, macOS arm64): `working`, `working ×2`, `waiting: web`, nothing when idle. A headless tmux (even `#(echo hi)`) renders no `#()` at all, so it proves nothing - attach a client. Starship shows a custom module's `symbol` even when the output is empty; the icon has to sit in a `(...)` group inside `format` for idle to hide it. ~40 ms per call.
- **Hardening from the M8ven trust-index review** (test [69]). Every MCP tool carries all four annotation hints (`annotate()` in mcp.js), true to what it does: status is read-only, nothing is destructive or open-world; directories such as OpenAI's reject a tool missing any. `vibe_stop` validates `outcome` against `OUTCOMES` and answers `isError`, since the schema's enum is a hint to the model and the string is echoed back. `getChimePath()` looks outcomes up with `Object.hasOwn`: `CHIMES["constructor"]` is truthy, and used to reach the generator call as a function that is not one of ours (or, for `toString`, cache a `chime_toString.wav`). `isInstalled()` passes `which`/`where` an argument vector, never a command string. Workflows declare `permissions:` and pin every action to a commit SHA, kept current by `.github/dependabot.yml` (github-actions only: the package has no dependencies to list). Do not move a `uses:` back to a tag, and do not add an npm ecosystem to dependabot. `actions/checkout` major bumps are ignored: 7.0.1's macOS/Node 18 test job hung in two of two runs (#56, at tests [54] and 26) while 4.x and the same job on main pass; cause not found. `setup-node` is at 7.0.0 (#55: test workflow green) - its first `publish.yml` run is the next release, which no PR could exercise.
- **`vibe_play`'s genre is client text.** Only a string counts (a number or object used to throw `.toLowerCase is not a function` and fail the call), and what is echoed back to the model is the name stripped to `[\w.-]` and capped at 24 characters, so a client cannot get a sentence returned through the fallback note. `SECURITY.md` states what the package touches (files, processes, the one network call, the MCP tools): keep it true, test [69] checks its install-scripts claim. It points at the repo's private vulnerability reporting (enabled in the repo settings; turn that off and the file is wrong). Commits in this checkout use the GitHub noreply address via a *local* `user.email` - the global one is a work address and must not be changed.
- **MCP seeds from the client's project, not the server's cwd** (#43, test [71]). An MCP server is launched once by its client in a directory the client picks, so `projectSeed()` from `process.cwd()` gave one arrangement per client. `resolveProject()` (mcp.js) picks, in order: `vibe_play`'s `project_dir` (validated: a string, absolute, <= 1024 chars, no NUL, `path.resolve`d so it matches the key `--here` saved - it is only hashed and used as a config key, never opened), the client's first **root**, then the cwd; `VIBE_SEED` still outranks all (`projectSource` says so). Roots are a *client* capability: only a client that declares `capabilities.roots` is asked, after `notifications/initialized` and again on `notifications/roots/list_changed`, by a request of ours with an id in our own space (`vibeaudio-roots-N`); the reply (a message with no `method`) is matched by that id, and **any** other response is dropped without an answer - `handleMessage()`'s tail would otherwise send "method not found" to the client for its own reply. `handleMessage(player, msg, session)` takes the session (`newSession(send)`); omitted, nothing is asked and nothing changes. `AudioPlayer.start({ project })` seeds from it and treats a different project as a restart, as it does a different genre. The directory also feeds `projectSettings(saved, dir)` and `musicEnabled(env, config, dir)`, so a genre, volume or music-off saved with `--here` applies over MCP (flag > env > project > global, as in the CLI). What was verified: Claude Code's client declares `roots: {listChanged: true}` (read from its 2.x binary), and **run live**: `claude -p --mcp-config` with `--strict-mcp-config` from two different folders called `vibe_status`, which answered `projectSource: "roots"` and the folder it was started in each time (the two seeds differ); Gemini CLI 0.62's `mcp list` health check declares **no** roots and launches a project-scoped server with its cwd in the project (so the cwd fallback is already right there); Claude Desktop, Antigravity and Codex were not checked, and for them the model-passed `project_dir` is the path. The roots exchange itself runs over real stdio against a fake client in the suite. Multi-root workspaces use the first root.
- **The daemon's lifetime is silence, not age.** It used to `setTimeout(shutdown, MAX_DAEMON_MS)` from spawn, so a turn longer than 15 minutes lost its music while the agent was still working. Now `MAX_DAEMON_MS` is how long a *session* may go without a hook (`listSessions()` drops it; every tool call's `hookResume` rewrites the file, which refreshes `ts`), the daemon exits when `sweep()` finds none left, and `DAEMON_CEILING_MS` (4 h) is only the backstop. Agents with no mid-turn hook (Cursor, Grok, Windsurf, Antigravity) have nothing to refresh `ts`, so for them a silent 15 minutes still ends the music, which is also what a crashed agent looks like. MCP's `MAX_PLAYBACK_MS` is unchanged: nothing there reports activity. `VIBE_MAX_DAEMON_MS` is internal, for the suite; test [45] keeps a turn alive past a 2.5 s limit with tool calls, then goes quiet and expects the daemon gone (fails on the old code).
- **The macOS/Node 18 CI hang is not one test's** (#56 and a third time on `a19fe28`, at tests [54], 26 and [63]; each time the job ran to its 15-minute limit and passed on rerun or on the next commit). The `--doctor` lookups were the first suspect and the hardening below is sound, but it was not the cause. What the hangs share is a short-lived system child (`which`, `ps`, a `--status`/`--doctor` CLI run) on that one runner image. Cause **still not found**. Test 26 (the `node` lookup) was where two of the occurrences stopped, and on 2026-10-08 it failed on Windows and hung on macOS in one run, so `isInstalled()` no longer spawns anything: it scans the `PATH` directories (PATHEXT on Windows, the execute bit elsewhere), which needs no `which` and cannot hang. `detectPlayer()` still spawns `which`, and the suite's fake-`which` stubs exist for it. Since then: `which` in `detectPlayer()` and `ps` in `daemonArgv()` carry a 3 s timeout with SIGKILL (a hook waits on all three, on every prompt; a timeout reads as 'not found' / 'not ours', both of which fail safe), and the suite wraps `spawnSync` (after `src/` has loaded, so code under test is untouched) so a child with no timeout of its own is killed at 120 s and the error names the command - the next occurrence says which one instead of 'the operation was canceled'.
- **A timeout is not a kill.** `spawnSync`'s `timeout` sends SIGTERM, a process stuck on hardware can ignore it, and `spawnSync` then waits on it indefinitely: `--doctor`'s `osascript`/`system_profiler` lookups did exactly that on a macOS CI runner (no audio device), once, in Dependabot's checkout-7 run - test [54] held the job for the 6-hour default. Test [70] runs a lookup that ignores TERM (`trap '' TERM; exec sleep`) and fails on the old code. macOS only.

Read per playback rather than cached, so exporting it applies on the next prompt.

**Synthesis** (`src/synth/`): `generator.js` holds the shared primitives — `noteToFreq()` (note name → Hz), oscillators (`sine`, `triangle`, `softPulse`, `analogSaw`), `createWavBuffer()` (raw Float samples → 16-bit PCM WAV `Buffer`), and the determinism helpers `makeRng()` (mulberry32), `hashString()` (FNV-1a), `pick()`, `rotate()` and `ornamentRng()`. Each genre exports `generate<Genre>Loop(durationSeconds, tier, seed, bar)` and returns a WAV buffer. `chime.js` generates the two outcome chimes and the attention chime (seed-independent).

Three rules hold across every generator:
- **Generation is pure and fully deterministic.** No `Math.random()` — dither and noise draw from the seeded stream, or the same seed would render different bytes and invalidate the cache.
- **The seed selects among curated variants, never invents harmony.** Each genre carries hand-written progressions diatonic to its key, with the bass line that spells those changes. Randomising notes freely produces bad bars; this cannot.
- **The bar rotates the curated variant; it never touches the ornaments.** `rotate(rng, options, bar)` draws exactly once, like `pick`, so a stream shared with ornaments below it is left in the same place and the ornaments stay put across the bars of one piece. That is what makes the bars read as one piece phrased differently rather than three unrelated loops — and it is why `bar = 0` is bit-identical to what `pick` returned. A generator that draws a second time for the bar, or that reseeds from it, breaks both.
- **Ornaments draw from `ornamentRng(seed)` in a fixed order, regardless of tier.** Gating a layer behind `tier >= 2` must not shift the choices other layers make, or tiers would stop being the same piece with more of it. A layer that draws from *inside* a tier gate therefore needs a stream of its own — `ornamentRng(seed ^ <constant>)`, as jazz's stabs and drone's noise bed do, or a separately-constructed `ornamentRng(seed)` when nothing else shares it. Jazz's brush noise was drawing from the file's shared stream inside a `tier >= 2` gate and held the invariant only because nothing happened to draw after it; the next ornament added below would have broken tier 1 silently. Scope the stream and the hazard cannot be reintroduced.

When adding a genre, follow that shape, honour `tier`, `seed` and `bar` (three curated variants, chosen with `rotate`, or test [51] fails), and wire it into `player.js`'s `generateLoop` switch and `AVAILABLE_GENRES`. Match its level to the existing ones (jazz sits at peak 0.64 / RMS 0.108) — a new generator is easy to write 3x too loud, and volume is applied after this, so a hot render just clips earlier.

`piano.js` is the sparse end of the melodic range: single struck notes (fundamental plus slightly-sharp inharmonic partials, so it reads as a piano rather than a bell) with silence between them and nothing sustaining underneath. Its tiers add notes into the existing gaps — 2, then 4, then 6 — rather than adding layers, so escalation never gives it a pulse.

`rain.js` and `ocean.js` are the other two non-melodic genres, built like drone from seeded noise. Rain is a band-passed bed plus droplets drawn as a fixed pool from a stream of its own - a tier only chooses how many to play, so tier 1 is tier 3's shower with drops left out. Ocean is exactly one swell cycle per loop (plus an exact second harmonic at tier 2+) so the tide tiles at the boundary; each variant carries a `level` make-up because a darker filter passes less noise. All three live in `NON_MELODIC_GENRES` and stay out of `random`.

`drone.js` is non-melodic: a held tone plus a swept noise bed, for people who cannot read past a melody. Its tiers add weight rather than movement, and its noise rng stream is drawn identically at every tier so the same seed keeps the same bed as the music escalates.

`src/render.js` is the piece as a *file* rather than as playback: the live player crossfades by re-spawning `LOOP_OVERLAP_MS` early, so anything writing a file has to stitch the bars itself or the seams click. `renderPiece()` lays out every bar of the phrase at each tier in turn and appends the success chime. `vibe --render` (cli.js) and `scripts/render-demo.js` both go through it — the landing page has to demo the audio the CLI actually produces, and it did not when the stitching lived only in the script. Renders at full scale, never at the configured volume: a file is played by something with its own volume control and a quiet render is not recoverable. WAV, because every platform plays one with nothing installed; `render-demo.js` adds macOS `afconvert` on top for the site's m4a, which is why it is the one macOS-only file here.

**MCP server** (`src/mcp.js`): exposes `vibe_play` / `vibe_stop` / `vibe_status` tools over stdio JSON-RPC for every client without a hook system (Claude Desktop, VS Code and the like, Gemini CLI releases older than its hooks; Antigravity before its hooks), backed by the same `AudioPlayer` class as the CLI wrapper. Nothing fires these tools automatically — the model chooses to — so the *when to call this* guidance lives in the tool descriptions, which every client shows the model, as well as in the `instructions` field, which the spec makes optional. Because a crashed client never sends `vibe_stop`, playback is capped by `MAX_PLAYBACK_MS` and also stops on stdin close. Tool responses report what actually happened (`start()`/`stop()` return booleans) rather than assuming success, and an unknown genre says it fell back to lofi instead of naming a genre nobody implements.

**Every request leaves with a response.** `tools/call` destructured `params` unconditionally, so a request without them threw, and the only thing catching it wrote to stderr — leaving the client blocked on a reply that was never coming. The line handler now separates a parse failure (no id to answer, stderr is all there is) from a handler throw (answer the id with `-32603`).

`detectTargets()` decides what to write to: config directory exists, or the CLI is on `PATH`. The directory is the reliable half — Cursor ships no CLI on `PATH` at all — and `PATH` covers a fresh install whose directory doesn't exist yet. `--tools claude,codex,cursor,grok,gemini,copilot,qwen` overrides it. They all share one daemon and one pid file — one user, one set of speakers — and the music plays **while any session is working**. Each session with a turn in flight is one file in `~/.vibeaudio/sessions/<session_id>.json` (`{transcript, offset, waiting, ts}`, written by temp file + rename, so no lock and no shared counter to race on); a payload with no `session_id` uses one shared `anon` slot. `--hook-start` writes the session's file and replaces the daemon only when no *other* session is working (so a genre change still lands on the next prompt); otherwise it leaves the music running, since restarting it would cut every other session's stream. `--hook-stop` removes the session's file, plays that session's own done chime, and stops the daemon only when nobody else is working. Before this, one shared `turn.json` held a single owner: session B finishing quickly killed the music while A was still working, and A then finished without a chime. A session untouched for `MAX_DAEMON_MS` is a crashed agent that never sent Stop and is dropped by `listSessions()`. The daemon passes the player a `minTier` floor (`working` sessions, capped at 3) so two sessions working is tier 2 at least and three is tier 3 — a floor that `Math.max`es with the time and reactive tiers, never lowers them, and is read per loop iteration, so a tier change lands at a loop boundary. Not built: per-session genres or mixing several streams. Because hooks fire as short-lived processes, playback lives in a detached daemon (`--daemon`, an internal mode) tracked by `~/.vibeaudio/daemon.pid`; `--hook-start` respawns it and `--hook-stop` SIGTERMs it, then plays the chime in the hook process itself.

`stopDaemon()` must confirm the pid before signalling it (`isOurDaemon()`, a `ps` command-line check). A pid file outlives a daemon that died without cleanup and the OS recycles pids, so an unverified kill eventually SIGTERMs an unrelated process — and `hookStart` calls `stopDaemon` on **every prompt**. It fails closed: an unverifiable pid is left alone, because a daemon we don't kill stops itself at `MAX_DAEMON_MS` while killing a stranger's process has no such ceiling. The check is posix-only; win32 trusts the pid.

The pid file is also the authority on **which** daemon plays (#42). Two prompts in different sessions arriving together could each find no daemon running and spawn one; the file then named the last, and the other played over it for the length of both turns (reproduced 6 runs in 10 with two concurrent `--hook-start`s). Each daemon checks the file on its `INTERRUPT_POLL_MS` poll and exits quietly once it names another pid. That is at most one poll of doubled audio, needs no lock, and also catches any other path that leaves an unnamed daemon. Test 29b produces the race deterministically by removing the pid file between two starts. After the fix, 10 of 10 concurrent runs leave one daemon.

Tests that touch the daemon must run in a child process with `HOME`/`USERPROFILE` overridden, never by setting `process.env.HOME` in the suite: `hooks.js` resolves `PID_FILE` from `os.homedir()` at require time, so an in-process override silently operates on the real `~/.vibeaudio` and clobbers a live daemon's pid file.

Because the hook command is an absolute path to this checkout, `installHooks()` first calls `ephemeralInstallReason()` and refuses when it's running from an `npx` cache — otherwise npm's eventual cache eviction leaves Claude Code firing a broken hook on every prompt. The guard runs before any write. `src/cli.js` wraps the whole `runHookAction()` dispatch in a try/catch so these (and malformed-settings aborts) print one line and exit 1 instead of a stack trace.

Every supported agent re-reads its hook file on each event rather than caching it at startup, so an install lands on the user's **next prompt** with no restart — verified by editing the file mid-session and watching the next daemon spawn with the new argv. Don't reintroduce restart instructions. The one lag is the daemon already playing, which keeps its argv until that next prompt replaces it.

**Waiting on the user, and turns that never reach `Stop`.** Each target lists only the optional `wait`/`resume`/`failure`/`end` events it was shown to fire (see the table above); Claude Code has all four plus transcript-based interrupts. For Claude Code this was established by reading Claude Code 2.1.195's bundle, then confirmed against the real binary over the stream-json control protocol the desktop app and IDEs use: `UserPromptSubmit → PreToolUse → PermissionRequest → (host approves) → PostToolUse → Stop → SessionEnd`, `session_id` on every one. Print mode with no permission prompt tool shows no dialog and fires no `PermissionRequest` — correctly, since there is nobody to wait on.

- **Wait.** Music playing through a dialog says "still working" to someone in another window when the agent is stuck on them. `PermissionRequest` and `Elicitation` → `--hook-wait` stops the daemon, marks that session `waiting` with a `waitKey()` (tool name, or `mcp:<server>`), stops the daemon **only if no other session is still working**, and plays the attention chime — a rising, unresolved fifth, deliberately unlike both outcome chimes, since reusing "done" would tell the user not to come back. Chosen over `Notification`'s `permission_prompt`, which only the terminal UI raises, after 6s idle. The chime is played **detached** (`stop({ detach: true })`): the agent waits on this hook before showing the dialog, and a chime played to completion held it back for its length. That replaced `async: true` on the entry, which Codex 0.125 may not accept; measured live, the chime now sounds 0.1s after the dialog is requested.
- **Notification waits** (Gemini, Copilot). Their dialog arrives as a `Notification` among others, so `hookWait` pauses only for `WAIT_NOTIFICATIONS` types (`permission_prompt`, `elicitation_dialog`, `ToolPermission`). They name no tool, so the wait key is empty, and an empty key resumes on whichever tool finishes next. Copilot's own `PermissionRequest` is not used: live, it fired before every permission check, with `--allow-all-tools` and no dialog.
- **Resume.** `PostToolUse`/`PostToolUseFailure`/`ElicitationResult` → `--hook-resume` clears the session's wait and respawns the daemon if none is running, only when its key matches — a parallel tool finishing is not the approval. `PermissionRequest` has no `tool_use_id`, hence names. These stay synchronous so a resume cannot land after the next tool's wait.
- **Interrupt.** Esc (or the stop button in the desktop app / an IDE) fires **no hook**: observed live, mid-reply fires nothing, and mid-tool fires a plain `PostToolUse` — not `PostToolUseFailure` with `is_interrupt`, which an earlier version relied on and which therefore never caught the common case. What Claude Code always does is append a user entry whose text is `[Request interrupted by user]` (or `… for tool use]`) to the transcript. The daemon polls every session's transcript every `INTERRUPT_POLL_MS` via `interruptWatcher()`, reading only bytes appended since that turn began, and drops the interrupted session silently — it exits once no session is left working, so Esc in one session leaves the others' music alone. `isInterruptEntry()` also catches a prompt another hook blocked - hooks run in parallel, so ours already started the music, and no `Stop` follows (print mode shows only `SessionEnd`, which an interactive session does not fire); Claude Code writes a `system` entry starting `UserPromptSubmit operation blocked by hook`, verified against the real binary. Only agents with a transcript are covered. A native blocker (token-ninja) is faster to start than a node hook, so its entry can land *before* `newTurn()` takes the offset - where the daemon never reads - so `newTurn()` also looks back over the tail for an entry stamped within `BLOCK_LOOKBACK_MS`, and `hookStart` then starts nothing. `isInterruptEntry()` matches the entry structurally (a `user` message with a text block starting with the marker), never by substring — transcripts quote that phrase constantly, including in any conversation about this feature. The offset is taken by `newTurn()` at the prompt and carried in that session's file, not at daemon spawn, because a resume respawns mid-turn: an approved tool interrupted with Esc still fires its `PostToolUse`, and the resumed daemon must see the interrupt that preceded it (it sweeps once before playing anything).
- **`StopFailure`** (API error, rate limit, prompt too long) fires *instead of* `Stop` and routes to `--hook-stop`; `outcomeFromPayload()` reads its `hook_event_name` as the verdict — Claude Code's first reachable failure chime.
- **`SessionEnd`** → `--hook-end` removes that session's file and stops the daemon silently only if no session is left working. It fires for idle sessions too, and one terminal closing must not silence another mid-turn. Fails closed on a session with no file.

`stopDaemon()` clears every session file unless called with `{ keepSessions: true }` — the hooks pass it because they decide per session what is still going on, and so does `--mute`, because a mute is about sound: the turns in flight still finish, reach `--report` and show in `--state`. `--stop` and uninstall end everything, emitting `ended` with `reason: "stop" | "uninstall"` for each session dropped (#24), the file removed first so the last line reads `idle`. Without the split a second dialog while already waiting erased the first wait, and the turn then ended with no chime. `hookStop` chimes when the session had a turn on record **or** the daemon was playing, since a turn that ends paused (a denied tool) still ended.

`--hook-stop` reads its stdin payload through `readPayload()` before chiming, because Cursor's stop event reports `status: "completed" | "aborted" | "error"` and that is the only way the failure chime is ever reachable under hooks. Claude Code's `Stop` payload carries no verdict and Codex's `StopRequest` has none either, so both keep success — inventing a failure the agent never claimed would be worse than a flat outcome. `readPayload()` must detach its listeners and `pause()` stdin when it finishes: a resumed stdin keeps the event loop alive by itself, so without that the hook process outlives its work on every turn and sits there until the agent times it out.

`--uninstall-hooks` sweeps **every** target, not just the detected ones — a hook left in the config of a tool that has since been uninstalled is exactly what an uninstall is for. It also calls `stopDaemon()` — from `cli.js`, not from `uninstallHooks()`, which stays a pure config edit so tests can call it against a throwaway file without touching the real `~/.vibeaudio/daemon.pid`. Without that stop, removing the hooks orphans a running player: nothing will send `Stop` again, and `npm rm -g` right after takes away the only binary that could kill it.

`--install-hooks --dry-run` runs the same `installHooks()` with `dryRun`, which skips the directory, the backup and the write and returns the file's current text beside the computed one; `printHookPlan()` diffs our entries per event (add / change / same / remove). The preview is the write minus the disk, so it cannot drift from what an install does.

**Plugin** (`.claude-plugin/`, `.codex-plugin/`, `hooks/hooks.json`, `hooks/codex.json`, `skills/vibe/`, #39): the repository root *is* the plugin, listed by its own `marketplace.json` with `source: "./"`, so publishing is a git push - `claude plugin marketplace add kiril6/vibeaudio`. One plugin serves four agents (`PLUGIN_AGENTS`): Claude Code; Codex 0.160, which reads `.claude-plugin/marketplace.json` and sets `CLAUDE_PLUGIN_ROOT` for plugin hooks; Copilot CLI, which loads `.claude-plugin/` manifests; and Qwen Code, which converts the plugin on install (copies the folder, substitutes the variable). `PLUGIN_FILES` maps each hooks file to the agents that read it, and `pluginHooksFile()` generates it from `TARGETS` minus the `tool` slot (reactive stays an `--install-hooks` option); test [60] fails on drift and prints the regenerate command. Each command is `node "${CLAUDE_PLUGIN_ROOT}/bin/vibeaudio.js" --hook-* --plugin --event <Name>`. Two files, not one, because **Claude Code 2.1.218 rejects an event it does not know** ("hooks.Interrupt: Invalid key in record") **and then loads none of the file** - so Codex's `Interrupt` cannot sit in the shared file. `.codex-plugin/plugin.json` is read by Codex before `.claude-plugin/` and never by Claude Code, and its `hooks: "./hooks/codex.json"` replaces Codex's default `hooks/hooks.json` (Codex's `load_plugin_hooks`; paths must start with `./`). Claude Code's manifest must *not* name its own file: naming `./hooks/hooks.json` there fails at load with "Duplicate hooks file detected". A shared file carries the union of its agents' events, so `runHookAction()` drops an event the running agent does not use (`expectedEvents()`): Copilot fires `PermissionRequest` before every permission check, dialog or not, and would otherwise pause the music on every tool call. The running agent comes from the environment each sets (`pluginAgent()`): `COPILOT_PLUGIN_ROOT` (Copilot, which also sets `PLUGIN_ROOT`, so checked first), `QWEN_PROJECT_DIR` (Qwen's hookRunner), `PLUGIN_ROOT` (Codex), else Claude Code, which sets only `CLAUDE_PLUGIN_*` / `CLAUDE_PROJECT_DIR`. `--plugin` also returns early when `userHooksInstalled(null, agent)` finds our entries in *that agent's* hook file: both present would restart the music every prompt and chime twice, and the installed ones win because they carry `--reactive`. Both manifests' `version` must equal `package.json`'s - a stale one makes `claude plugin update` say "already at the latest", and Codex compares it too - so the `version` npm script rewrites both and `publish.yml` refuses a tag where any differs. `claude plugin validate .` passes with one warning (a `CLAUDE.md` at the plugin root is not loaded as context), which `--strict` turns into a failure; that file is this one, so CI does not use `--strict`. Verified: validate on both Claude manifests; a live `claude -p --plugin-dir .` load on 2.1.218 (no load error, the plugin's `SessionEnd --event SessionEnd` hook ran, exit 0); the hook command with `CLAUDE_PLUGIN_ROOT` containing a space; Codex's manifest discovery and `hooks` override from rust-v0.160.0 source. Codex verified live on 0.160.0 in a throwaway `CODEX_HOME` with the user's `auth.json` copied in: `codex plugin marketplace add kiril6/vibeaudio` + `codex plugin add vibeaudio@vibeaudio` from GitHub, then a real `codex exec` turn fired `UserPromptSubmit` / `PostToolUse` / `Stop` and produced `started` / `finished` and a history line; with `--install-hooks` entries also present both sets fired and only one `started`/`finished` was written (the step-aside). Plugin hooks need Codex's one-time trust like any hook; the run used `--dangerously-bypass-hook-trust`, safe there because ours were the only hooks. `codex exec` fired no `SessionEnd`. Codex caps `SessionEnd` and `Interrupt` hooks at 3s (`SESSION_END_MAX_TIMEOUT_SEC`) and warns on every run past it, so `TARGETS.codex.entry(command, event)` writes 3 for those two, installed and plugin alike. Not verified: Copilot and Qwen (not installed), a real Gemini turn (no Gemini CLI login here), and a full `claude plugin install` (the sandboxed config dir needs a login). The README offers the plugin for Claude Code and Codex only. Anthropic's directory (claude.ai/directory/manage) was considered and skipped: it lists on claude.ai and Cowork, where hooks do not load, and the official marketplace takes no submissions.

**Gemini CLI extension** (`scripts/gemini-extension.js`, `.github/workflows/gemini-extension.yml`, #40): Gemini reads an extension's hooks from a fixed `hooks/hooks.json` in its own event names, and the repository's file at that path is Claude Code's, so the extension cannot be the repository root. It does not need to be: `gemini extensions install https://github.com/kiril6/vibeaudio` fetches the latest **release** and installs its asset when there is exactly one (`findReleaseAsset`; a name containing darwin/linux/win32 is skipped), else the source tarball. The workflow builds the extension from the release's tag on `release: published` and uploads `vibeaudio-gemini-extension.tar.gz`, a single top-level `vibeaudio/` directory that Gemini flattens. Keep it the release's only asset. The build ships `bin/`, `src/`, `package.json`, a `gemini-extension.json` and hooks generated by `pluginHooksFile(["gemini"], "${extensionPath}${/}bin${/}vibeaudio.js")` - Gemini substitutes both variables itself (`loadExtensionHooks`, `recursivelyHydrateStrings`). Hooks run with `--plugin`, and `pluginAgent()` reads `GEMINI_PROJECT_DIR` (Gemini's hookRunner sets it; Qwen, a fork, sets it too and is checked first), so installed Gemini hooks win as they do for the plugin. Verified with Gemini CLI 0.62.0 in a throwaway HOME: `extensions validate` and a local `extensions install` (a local path asks to trust the folder), then the installed hook commands, substituted as Gemini does, run a full turn - start, permission wait, resume, finish, history line. Test [64] covers the build, a turn and the step-aside. The GitHub install was verified on v0.14.0, the first release with the asset: `gemini extensions install https://github.com/kiril6/vibeaudio` recorded `type: github-release`, `releaseTag: v0.14.0`, and its hooks ran a full turn. Not verified: a real Gemini turn (no signed-in Gemini CLI here); until then the README does not offer it. Releases before v0.14.0 carry no asset, and their source tarball has no `gemini-extension.json`, so installing one fails rather than half-works.

**`/vibe`** (`<claudeConfigDir()>/commands/vibe.md`) is installed with the Claude Code target and removed by `--uninstall-hooks` — from `cli.js`, not from `installHooks()`, so tests that install into a temp settings file never touch the real commands directory. It is a prompt asking the model to run the CLI (`--status`, `--mute`, `--stop`, or a reinstall that keeps the current volume/genre read from `--status`), not a hook. `SLASH_MARK` identifies our file: a user's own `vibe.md` is neither overwritten nor deleted.

Settings writes must stay non-destructive: the file belongs to the user and usually holds other tools' hooks. `isVibeHook()` identifies our entries by `VIBE_HOOK_FLAG` (`--hook-start`/`-stop`/`-tool`/`-wait`/`-resume`/`-end`; `--status` reads the same pattern), `setHook()` replaces rather than appends (idempotent reinstall), malformed JSON aborts instead of being overwritten, and the prior file is copied to `settings.json.vibeaudio.bak` — **once, and never overwritten**. The second `--install-hooks` reads a file that already holds our entries, so re-backing up would replace the user's real pre-VibeAudio config with a copy of our own last install, while `--uninstall-hooks` goes on calling it "your pre-VibeAudio config backup". Only the first one is that.

`resolveTargets()` tests `explicit !== null`, not truthiness: `--tools ""` is typed, not absent, and treating it as absent fell through to auto-detection and installed for *every* agent on the machine — the exact opposite of naming one.

`promptInteractive()` returns intent (`installHooks`, `reactive`) and never writes config itself — `cli.js#applyMenuSelection` performs the install so both entry points share one code path and one report. The delivery and reactive questions are asked only for entries with a `hookTarget`; asking elsewhere would offer a control that does nothing. Choosing hooks in the menu is **setup, not launch**: `applyMenuSelection()` (cli.js) installs, prints one line ("VibeAudio vX is hooked into: A, B", with the installed version and a keep-current hint, never leading with the one just picked) saying nothing was started and naming **every** agent VibeAudio is hooked into on the machine (`userHooksInstalled()` per target, so a second run lists the first run's agent too) with the commands to open them, and returns without running the tool, because someone with several agents may want to set one up now and open it later, and the music plays from the first prompt either way. Only "just launch it" and "this session only" go on to start the tool. An install that throws (npx checkout, malformed settings) is an error with exit 1, not a launch without the hooks that were asked for (it used to launch anyway, when install was a step before starting). Test [75].

**The launcher's hook-capable entries are derived from `TARGETS`, not listed again.** `AI_TOOLS` carries a `hookTarget` id and `hookTargetOf()` resolves it against `TARGETS`, throwing on an id that isn't there. A second hand-kept list is how Grok became a complete hook target — its own file, its own event names, a row in the README — that the menu had no entry for at all: picking it offered the wrapper and nothing else. `hookTarget` is deliberately not the same field as `check`, because they differ: Cursor's CLI is `cursor-agent` while its target id is `cursor`, and a list keyed on the wrong one installs for the wrong agent. Test [38] fails if any target has no launcher entry, so adding a target forces the menu question to be answered rather than forgotten.

`promptInteractive()` takes `hooksInstalledFor(id)`, a predicate, not a boolean. The caller cannot know which tool the user will pick until the menu has run, so the old boolean was computed for Claude every time — telling a Grok user with Grok hooks already installed that they had none, and offering to install what was already there.

Cursor **is** in the launcher: it ships `cursor-agent`, which `TARGETS.cursor.cmd` has always named and `detectTargets()` has always probed on `PATH`. This file previously said it had no CLI to launch; that was stale, not deliberate.

**Reactive mode** (`--reactive`, opt-in) adds a pre-tool-use hook that reads the agent's JSON payload from stdin and writes a tier to `~/.vibeaudio/intensity` (`TOOL_TIERS`). The tiers were checked against 30,532 real tool calls: `Task` had been renamed `Agent`, so the heaviest thing in a turn was silently landing on the fallback, and a third of all calls are MCP tools (`mcp__<server>__<tool>`, or `MCP:<tool>` on Cursor) which cannot be enumerated and keep tier 2 deliberately. Tools meaning "the agent has stopped and is waiting for the human" (`AskUserQuestion`, `ExitPlanMode`) sit at tier 1 even though they aren't lookups. Claude Code, Codex and Cursor put the tool's name in `tool_name`; **Grok spells it `toolName`** — `hookTool()` reads both, because reading only one would silently pin that agent to the fallback tier forever. `TOOL_TIERS` carries every vocabulary (Claude's PascalCase, Codex's snake_case, Cursor's short names) in one flat map because they don't collide. The daemon passes `readIntensity` to `AudioPlayer.start()` as the `intensity` option, and `playLoop()` prefers it over the time-based tier, falling back when there's no signal. It stays off by default because music that reacts to every tool call is music the user notices — the opposite of the product's goal. `hookStart`/`hookStop` clear the intensity file so one prompt's activity can't leak into the next.

**Stuck signal** (`src/synth/tension.js`, `isStuck()` in hooks.js): the one thing louder music cannot say. `hookResume` already runs on every tool call, so it keeps `recent` - the last `STUCK_WINDOW` (8) outcomes, 1 for a `PostToolUseFailure` that is not `is_interrupt` - in the session file; `hookStart` writes a fresh session, so every prompt starts clean. `isStuck` is `STUCK_FAILURES` (4) of those. The threshold was measured, not chosen: over 4,497 real Claude Code turns (46,032 tool calls, 3.8% failing), 4-of-8 fires in 0.9% of turns at a median minute 3, and those turns ran a median 3.3 minutes more. "3 in a row" misses the common loop (a successful edit sits between every failing test run); "3 of 8" fires in 2.4%. Verified live against Claude Code 2.1.195: a Bash non-zero exit and a Read of a missing file both fire `PostToolUseFailure` (`error`, `is_interrupt` in the payload); successes fire `PostToolUse`. Copilot and Qwen route the same event name but were not run for this; Codex, Cursor, Gemini, Grok and Windsurf have no failure event, so they never go stuck - better than guessing from `tool_response`. The daemon passes `tension: () => working(listSessions()).some(isStuck)` to the player, read per loop like `minTier`; `getAudioPath(..., tension)` renders a `_x` cache file, `addTension()` mixing a heartbeat (lub-dub at ~55 bpm, a whole number of beats per loop) on `GENRE_KEYS`' tonic, held between 110 and 220 Hz because laptop speakers lose anything lower. It stays 0.15s clear of both ends so the boundary fades and crossfades are untouched; peak stays under 0.9 on every genre and the layer sits 7-14 dB under the music. `notify()` fires once, on the crossing, never per failure. ponytail: two parallel tool calls in one session can read-modify-write over each other and lose one outcome; a heuristic over eight calls tolerates that.

**Public state: `--state` / `--events`** (`agentState()`, `emitEvent()`, `followEvents()` in hooks.js). The cross-agent event mapping is the asset, and the music is one consumer of it; these make others possible without reading internal session files. `agentState()` maps each session file to `working` / `stuck` / `waiting`, and `status` is the most urgent (`STATE_RANK`: waiting > stuck > working > idle). Session files now carry `project` (payload `cwd`, taken in `newTurn()`), so an event fired with no payload, such as the daemon's `interrupted`, can still name it. Each hook appends one line to `~/.vibeaudio/events.jsonl` **after** the session file is written, so the line's `status` is the state the event left behind: `started`, `waiting`, `resumed`, `stuck`/`recovered` (on the crossing only, never per tool call), `finished` (+`outcome`), `interrupted` (the daemon's transcript sweep, or Codex's `Interrupt` hook through `hookEnd`), `ended`. Never gated by a mute: a mute is about sound, and a light watching this is not sound. Never throws. The log **rotates** to `.1` past 256 KB rather than being trimmed in place, because `followEvents()` tracks a byte offset and inode: a trim would have it re-print the lines it kept, while a fresh inode means "start at 0" is correct. Polled at 250 ms, not `fs.watch` (unreliable across the three platforms). `--events` exits quietly on EPIPE so `| head` works. `v: 1` is the format version. `ended` also comes from `--stop` and uninstall, with a `reason` (#24). Test [62] runs it end to end, including a follower across a rotation. `interrupted` from the daemon's sweep is asserted in the Esc test (event, session, `project` from the session file, `status: idle`; fails with the `emitEvent` removed). The README's `say` pipeline was run for real: `jq --unbuffered` streams each `waiting` as it happens. tmux's `status-interval` defaults to 15 s, so the README sets 5.

**HUD** (`src/hud.js`): animates an ASCII waveform in the terminal **title bar only** — the wrapped tool may own the screen by the time music starts, so drawing inline would corrupt a full-screen TUI. `stop()` is inert unless `start()` ran and is idempotent, since `cleanup()` can be reached from more than one path.

## Finishing a task

A change is not done at the code. Before calling a task finished, go through this, and say in the closing message which items applied:

- **Tests**: `npm test` passes, with a test that fails without the change. Anything that touches the audio cache, `HOME` or the daemon follows the rules above.
- **README.md**: the feature list, the relevant table (hook targets and events, flags, env vars, troubleshooting), the FAQ line that the change makes stale, and the `--help` text in `src/cli.js` when a flag changes. Search for the old wording and for counts ("8 genres", "seven agents") - they go stale silently.
- **docs/index.html** (the GitHub Pages site, served from `main`): badges, feature cards and counts. New audio means `scripts/render-demo.js`, committing only the new clips - m4a re-encodes are not byte-stable.
- **CLAUDE.md**: the architecture note for any new mechanism, invariant or hazard, including how it was verified.
- **The issue**: comment with what shipped and what is still open, and close it only when the issue's own acceptance is met - something written from docs alone is not "verified".
- **Release**: only when asked. `npm version`, `git push --follow-tags`, a GitHub release with notes, then poll the registry directly (`curl registry.npmjs.org/vibeaudio/latest`) - `npm view` lags several minutes. Never `npm publish` by hand.

## Conventions

- Every module in `src/synth/` is pure — no I/O, just math producing sample arrays — keep it that way so `test/test-synth.js` can assert on generator output directly.
- CLI flags/env vars are parsed once in `src/cli.js#parseArgs`, which is unit-tested directly (imported into `test/test-synth.js`) — extend that function's `while` loop for new flags rather than parsing args elsewhere. A new flag that takes a value belongs in `VALUE_FLAGS` too, or a trailing `vibe --yourflag` falls through every branch into `cmdArgs` and the wrapper reports ENOENT on a program named after the flag. An argument starting with `-` that matches nothing is an error, not a command: `vibe --typo npm test` used to report `spawn --typo ENOENT`, an error about the wrong thing. `--` is the escape hatch and ends our flags, so a command that genuinely starts with a dash is still reachable. Flags *after* the command were never ours and are unaffected — the loop stops at the first non-flag. **No flag may be detected by scanning `process.argv`** — `--mcp` was, so `vibe npm test --mcp` started a server instead of running the tests; the parse loop stops at the first non-flag, which is what keeps the child's flags the child's.
- `bin/vibeaudio.js` catches `run()`'s rejection. It is async, so anything escaping it is an unhandled rejection: a stack trace, and a hard crash on Node 18+. Likewise, only the interactive *menu* exits quietly on throw — wrapping the launch in that same catch turned every real failure into a silent exit 0, which for a wrapper is the worst available outcome (`vibe && deploy` chains on a run that never happened).
- The HUD reports the chime that **played** (`chimed`), not the one the outcome implies: `--no-chime` and a mute both leave it silent, and announcing a chime nobody heard sends the user looking for a broken speaker.
- The suite renders into its own cache: `test/test-synth.js` sets `VIBE_CACHE_DIR` (internal, read once by `player.js`) to a temp directory before anything requires `player.js`, every child inherits it, and it is removed on exit (#38). In the real `~/.vibeaudio/cache`, live hooks running from this checkout pruned a test's seed directory mid-run (ENOENT on `s42/loop_jazz_t2.wav`), and `pruneSeedDirs` keeping only three projects let the suite evict a real project's audio — test 27 used to leave an `s42` behind on every run. A test that touches the cache should still delete its seed directory afterwards: the isolation is the protection, that is the tidiness. `--clear-cache` removes only our entries (`v*` key directories, loose WAVs), never the root, because an overridden root may hold other things. Test 17b; verified by listing the real cache before and after a full run.
- A test that exercises an install path must redirect `HOME`/`USERPROFILE` to a temp directory. The assertion exists because the bug *writes config*, so a regression has to land somewhere disposable rather than in whoever runs the suite.
- Volume arrives as a string from env/flags and as a number from MCP, so every entry point goes through `player.js#normalizeVolume`. A second hand-rolled clamp is how `VIBE_VOLUME=loud` reached the player as `NaN`.
- `test/test-synth.js` runs on Linux, macOS and Windows in CI. Spawn `process.execPath` rather than `sleep`/`true`/`false`, and guard posix-only assertions on `process.platform`.
- A test that waits for something to happen (a daemon to exit, a backend to log a play) polls for it against a deadline; it never sleeps a fixed time and then asserts (#44). A daemon busy rendering handles SIGTERM late, and on a loaded CI runner a fixed 400 ms is a coin toss. A fixed sleep is only for a negative check, where it is the window a wrong outcome would have had to show up in. A probe that is the daemon's parent must `await` between checks rather than block, or it never reaps the child, and a zombie still answers `kill(pid, 0)`. Verified by running the suite with `yes` saturating every core.
